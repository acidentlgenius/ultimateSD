3 follow-ups that break people on URL shortener design

You can explain the happy path — API, DB, redirect — and still lose the round when the interviewer keeps asking "what if…"

TinyURL is a classic fresher question. These three follow-ups separate memorized diagrams from real understanding.

1 / 5
Ultimate SD
follow-up #1
Interviewer asks
"How do you generate short codes without collisions?"
  • Hashing the long URL and taking the first 7 chars collides — two URLs can map to the same code.
  • Better: global auto-increment ID → encode to Base62 (a–z, A–Z, 0–9). URL-safe, predictable length.
  • 7 chars in Base62 ≈ 3.5 trillion codes — plenty for most estimates.
Common trap

Saying "we'll use MD5" without explaining what happens when two hashes share the same prefix.

2 / 5
Ultimate SD
follow-up #2
Interviewer asks
"Reads are 10× writes — where does cache sit, and what do you evict?"
  • Put Redis (or Memcached) between the app and DB on the redirect path.
  • Cache key = short code, value = long URL. On miss, read DB and backfill cache.
  • You can't cache everything — use LRU. Rule of thumb: cache ~20% of daily read traffic (hot URLs).
Common trap

Adding "we'll use a cache" with no eviction policy, no miss path, and no read/write split.

3 / 5
Ultimate SD
follow-up #3
Interviewer asks
"User wants custom alias 'grokking' but it exists. 301 or 302 redirect?"
  • Custom alias: uniqueness check before insert. Return 409 if taken — don't silently overwrite.
  • 301 = permanent. Browsers cache it — less load on you, but harder to track clicks reliably.
  • 302 = temporary. Browser hits your server each time — better for analytics, more latency.
Bonus they might ask

Expired links: lazy delete on access + background worker to sweep stale rows.
