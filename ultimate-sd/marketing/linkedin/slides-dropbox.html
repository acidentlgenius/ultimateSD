3 follow-ups that break people on Dropbox design

Everyone can say "store the files in S3." The round isn't lost on storage — it's lost on sync: what happens when files change, devices go offline, and edits collide.

Dropbox looks like a glorified FTP server. These three follow-ups separate memorized diagrams from real understanding.

1 / 5
Ultimate SD
follow-up #1
Interviewer asks
"A user edits 1 line of a 2 GB file — what uploads?"
  • Split every file into ~4 MB chunks and hash each one with SHA-256 — the hash is the chunk's identity.
  • After an edit, unchanged chunks hash the same. Only the changed chunks upload — that's delta sync.
  • Bonus: if any user anywhere already uploaded a chunk with that hash, it's never stored again. Dedupe saves petabytes.
Common trap

Re-uploading the whole 2 GB because one paragraph changed. Chunking and delta sync are the question.

2 / 5
Ultimate SD
follow-up #2
Interviewer asks
"Two devices edit the same file offline — who wins?"
  • Last-writer-wins silently deletes one person's work — catastrophic for a product that promises never to lose data.
  • Dropbox's answer: each commit carries the version it was edited against. First commit wins; the second becomes "budget (conflicted copy — Bob's MacBook).xlsx".
  • The metadata DB is the single source of truth — a version doesn't exist until its commit lands there. Blob storage is just a bag of chunks.
Common trap

Saying "last write wins" for user files. Punting the merge to a human is the senior answer, not a cop-out — the system can't safely merge arbitrary bytes.

3 / 5
Ultimate SD
follow-up #3
Interviewer asks
"How do other devices find out about changes?"
  • A notification service pushes a tiny invalidation — "file X is now version 7" — to the user's other devices when a commit lands.
  • Long polling vs WebSocket: millions of mostly-idle devices polling every 5 seconds would melt the metadata tier. Long polling gets near-instant sync at a fraction of the requests.
  • The device then fetches the new chunk list from metadata and pulls only the chunks it lacks — never the whole file.
Common trap

Clients polling for changes. 10M devices asking "anything new?" every 5 seconds is 2M QPS of nothing.
