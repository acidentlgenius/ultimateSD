3 follow-ups that break people on rate limiter design

Everyone can say "100 requests per minute, return 429". The round is decided by what happens when the interviewer keeps asking "but what if…"

A rate limiter looks like a utility class. That's the trap — it's really a question about algorithms, shared state, and failure modes.

1 / 5
Ultimate SD
follow-up #1
Interviewer asks
"You picked a fixed window of 100 req/min. What's wrong with it?"
  • The counter resets at the boundary. Send 100 requests at 0:59 and 100 more at 1:01 — that's 200 requests in 2 seconds, all allowed.
  • Fix: sliding window counter — a weighted blend of the current and previous windows. Two counters per client, no boundary hole.
  • The approximation error is negligible in practice — Cloudflare measured well under 1% mismatch on real traffic.
Common trap

Proposing fixed window and waiting to be asked. Volunteering the boundary-burst problem yourself is an instant senior signal.

follow-up #2
Interviewer asks
"Client bursts are legitimate — a mobile app syncing after being offline. Which algorithm?"
  • Token bucket. The bucket refills at a steady rate; each request spends a token. Saved-up tokens allow a burst.
  • Two knobs to explain: refill rate = sustained throughput, capacity = max burst. 100 tokens refilling at 10/sec allows a burst of 100, then sustains 10 req/sec.
  • This is what Stripe and AWS use — citing that is fair game in the interview.
Common trap

Reciting all five algorithms without picking one. A comparison with no recommendation reads as memorization — take a position.

follow-up #3
Interviewer asks
"Nice. Now enforce that limit across 10 API servers behind a load balancer."
  • Local counters on each node multiply the limit — a client spread across 10 nodes gets ~10× the quota.
  • Standard answer: one counter per client in a central Redis. But GET → check → INCR is two round trips — two nodes can both read 99 and both allow.
  • Fix the race with a Lua script: Redis runs check + decrement atomically as one operation.
Bonus they might ask

Redis is down — now what? Fail open for normal traffic (the limiter must not become the outage), fail closed for login and OTP endpoints.
